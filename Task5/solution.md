# Архитектурное решение по кешированию

## 1. Мотивация

Текущая производительность MES-системы не удовлетворяет потребностям бизнеса:

- **Медленная загрузка дашборда оператора:** Страница со списком заказов (с фильтрацией и пагинацией) загружается несколько секунд, что снижает эффективность работы операторов и напрямую влияет на скорость обработки заказов.
- **Длительный расчёт стоимости заказа:** Синхронный вызов `MES API` для расчёта цены 3D-модели может занимать от 2 до 30 минут, вызывая таймауты у клиентов B2B API и ухудшая пользовательский опыт.

**Цели внедрения кеширования:**
1. Сократить время ответа дашборда MES до **менее 200 мс** для повторяющихся запросов.
2. Снизить нагрузку на базу данных `MES db` и сервер приложений `MES API`.
3. Обеспечить возможность горизонтального масштабирования за счёт разгрузки основного хранилища.

**Область кеширования:**
- **Чтение:** Список заказов для дашборда оператора (эндпоинт `GET /api/orders?status=...&page=...`).
- **Чтение:** Результаты расчёта стоимости для ранее обработанных 3D-моделей (эндпоинт `GET /api/orders/{orderId}/price`).

Изменение статусов заказа (запись) остаётся без кеширования на первом этапе, чтобы избежать усложнения логики инвалидации.

## 2. Предлагаемое решение

### 2.1. Тип кеширования: серверное

Выбрано **серверное кеширование** по следующим причинам:
- **Клиентское кеширование (HTTP-заголовки `Cache-Control`)** не подходит, так как дашборд оператора требует актуальных данных при каждом обновлении страницы, а разные операторы должны видеть консистентную картину назначенных заказов.
- **Общий кеш на стороне сервера** позволяет централизованно управлять инвалидацией и снижает суммарную нагрузку на базу данных.

### 2.2. Паттерн кеширования: Cache-Aside (Lazy Loading)

Для операции **чтения списка заказов** предлагается использовать паттерн **Cache-Aside**.

**Обоснование выбора:**
| Критерий | Cache-Aside | Read-Through | Write-Through | Write-Behind |
|----------|-------------|--------------|---------------|--------------|
| **Устойчивость к сбоям кеша** | ✅ Высокая — при отказе кеша приложение обращается к БД напрямую | ❌ Низкая — кеш становится единой точкой отказа | ❌ Запись блокируется при недоступности кеша | ❌ Риск потери данных при сбое кеша |
| **Гибкость модели данных** | ✅ Модель в кеше может отличаться от БД (агрегированные данные для дашборда) | ❌ Модель должна совпадать | ❌ Строгая синхронизация схем | ❌ Ограниченная гибкость |
| **Влияние на задержку записи** | ✅ Отсутствует (запись идёт напрямую в БД) | ✅ Отсутствует | ❌ Дополнительная задержка на синхронную запись в кеш | ✅ Низкая (асинхронная запись) |
| **Сложность реализации** | ✅ Низкая — логика кеширования инкапсулирована в приложении | Средняя — требуется интеграция с провайдером кеша | Средняя | Высокая — требуется обработка асинхронных сбоев |
| **Консистентность данных** | ⚠️ Возможна временная неконсистентность (решается TTL + инвалидацией) | Высокая | ✅ Очень высокая | ❌ Низкая (eventual consistency) |

**Почему не подходят другие паттерны:**
- **Read-Through / Write-Through** требуют, чтобы кеш находился на пути всех операций чтения/записи. В текущей архитектуре `MES API` напрямую взаимодействует с PostgreSQL, и внедрение промежуточного слоя увеличило бы задержки и стало бы единой точкой отказа.
- **Write-Behind** усложняет отладку и восстановление после сбоев из-за асинхронной записи в БД, что критично для бизнес-транзакций изменения статуса заказа.
- **Refresh-Ahead** предполагает предварительное обновление данных до истечения TTL, что увеличивает нагрузку на БД и сложность прогнозирования времени жизни. Для дашборда с фильтрами по статусам сложно предугадать, какие данные потребуются.

**Итог:** **Cache-Aside** даёт наилучший баланс между производительностью, надёжностью и простотой внедрения.

### 2.4. Стратегия инвалидации кеша

Для обеспечения консистентности данных после изменения статуса заказа применяется комбинированная стратегия:

| Стратегия | Применение | Обоснование |
|-----------|------------|-------------|
| **Инвалидация по ключу (Key-based)** | При изменении конкретного заказа удаляются ключи: `order:{orderId}` и шаблон `orders:list:*` (все кешированные списки). | Обеспечивает немедленную актуальность данных для последующих запросов. |
| **Временная инвалидация (TTL)** | Для ключей списков (`orders:list:status={s}:page={p}`) устанавливается TTL = 30 секунд. | Гарантирует, что даже при пропуске события инвалидации (например, сбой сети) данные обновятся не позднее чем через 30 секунд. |
| **Программная инвалидация** | В коде `MES API` при обновлении статуса явно вызывается метод `cache.invalidate(pattern)`. | Даёт полный контроль над моментом удаления кеша. |

**Почему не подходят другие стратегии:**
- **Только временная инвалидация** — недопустима для критичных бизнес-данных: оператор может увидеть устаревший статус заказа до 30 секунд, что приведёт к конфликтам при назначении.
- **Инвалидация на основе запросов** — не применима, так как нет гарантии, что пользователь запросит обновлённые данные в ближайшее время.
- **Программная инвалидация без TTL** — риск накопления «мусора» в кеше при пропуске события инвалидации (сбой сети, исключение).

### 2.5. Детали реализации

**Технология кеша:** **Redis** (размещается как отдельный контейнер/сервис в инфраструктуре).

**Структура ключей:**
- `order:{orderId}` → детали одного заказа (JSON).
- `orders:list:status={status}:page={page}:size={size}` → агрегированный список заказов (массив ID или DTO).

**Логика в `MES API`:**
```csharp
public async Task<List<OrderDto>> GetOrdersAsync(string status, int page, int pageSize)
{
    string cacheKey = $"orders:list:status={status}:page={page}:size={pageSize}";
    var cached = await _redis.StringGetAsync(cacheKey);
    if (!cached.IsNull)
        return JsonSerializer.Deserialize<List<OrderDto>>(cached);

    var orders = await _db.Orders
        .Where(o => o.Status == status)
        .OrderByDescending(o => o.CreatedAt)
        .Skip(page * pageSize)
        .Take(pageSize)
        .ToListAsync();

    await _redis.StringSetAsync(cacheKey, JsonSerializer.Serialize(orders), TimeSpan.FromSeconds(30));
    return orders;
}

public async Task UpdateOrderStatusAsync(int orderId, string newStatus)
{
    // 1. Update DB
    var order = await _db.Orders.FindAsync(orderId);
    order.Status = newStatus;
    await _db.SaveChangesAsync();

    // 2. Invalidate cache
    await _redis.KeyDeleteAsync($"order:{orderId}");
    // Удалить все списки (можно использовать SCAN + DEL по шаблону)
    var endpoints = _redis.Multiplexer.GetEndPoints();
    foreach (var endpoint in endpoints)
    {
        var server = _redis.Multiplexer.GetServer(endpoint);
        var keys = server.Keys(pattern: "orders:list:*").ToArray();
        if (keys.Any())
            await _redis.KeyDeleteAsync(keys);
    }
}
```

### 2.6. Политика безопасности
- Чувствительные данные (`customerId`) не попадают в кеш дашборда оператора (только `orderId`, `status`, `assignedOperator`).
- Доступ к Redis ограничен внутренней сетью, аутентификация по паролю.

## 3. Заключение
Предложенное решение на базе паттерна Cache-Aside с Redis и комбинированной инвалидацией (по ключу + TTL) позволит:
- Уменьшить время загрузки дашборда MES с **2 – 5 секунд** до **<100 мс** (при попадании в кеш).
- Снизить нагрузку на PostgreSQL на **70 – 80%** для операций чтения списков.
- Сохранить высокую надёжность системы за счёт устойчивости Cache-Aside к отказу кеша.

Внедрение может быть выполнено в течение одного спринта силами разработчика C# и DevOps-инженера.
