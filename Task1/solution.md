# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ архитектуры и идентификация проблем

На основе предоставленной C4-диаграммы (`jewerly_c4_model.drawio`) и описания бизнес-контекста были выявлены следующие проблемные места, сгруппированные по категориям.

### 1.1. Производительность и масштабируемость

| ID | Проблема | Проявление | Корневая причина |
| :-- | :--- | :--- | :--- |
| **P-01** | Медленная загрузка дашборда MES (список заказов). | Операторы жалуются на долгую загрузку страницы. Пагинация и фильтры не помогли. | Отсутствие кеширования часто запрашиваемых данных. Вероятно, сложные SQL-запросы к `MES db` без оптимизации индексов под сценарий "получить N последних заказов". |
| **P-02** | Длительный расчет стоимости заказа (MES API). | Расчет занимает 2-3 минуты, в сложных случаях до 30 минут. | Синхронное ожидание HTTP-запроса при длительной CPU/GPU-bound операции расчета 3D-модели. Это блокирует ресурсы сервера и вызывает таймауты у клиентов (особенно API-пользователей). |
| **P-03** | Единая точка отказа и отсутствие горизонтального масштабирования. | Каждое приложение (Shop API, MES API, CRM API) и БД имеют по одному инстансу. | Инфраструктура не готова к росту нагрузки. Падение одного инстанса ведет к полной недоступности сервиса. |
| **P-04** | Нагрузка на основную БД Shop DB. | Прямые запросы от Shop API и CRM API к одной БД. | `Shop DB` обслуживает и магазин, и CRM, что создает конкуренцию за ресурсы ввода/вывода. |

### 1.2. Надежность и отказоустойчивость (Resilience)

| ID | Проблема | Проявление | Корневая причина |
| :-- | :--- | :--- | :--- |
| **R-01** | Потеря заказов и рассинхронизация статусов. | Клиенты жалуются на просрочку в несколько месяцев. Заказы "зависают". | Проблемы с обработкой сообщений в RabbitMQ. Возможны: отсутствие DLQ (Dead Letter Queue), ошибки десериализации, отсутствие механизма повторной обработки (Retry) с экспоненциальной задержкой. |
| **R-02** | Отсутствие Circuit Breaker при интеграции с MES API. | Приложение онлайн-магазина зависает или падает, если MES API долго отвечает или недоступен при расчете цены. | Нет паттерна Circuit Breaker (предохранитель) на стороне `Shop API` при вызове `MES API`. |
| **R-03** | Ручной деплой в Prod и Release. | Низкая частота релизов, сложность отката. | CI/CD автоматизирован только до стадии тестирования. Ручной деплой повышает риск человеческой ошибки и замедляет доставку хотфиксов. |

### 1.3. Наблюдаемость (Observability) и процессы

| ID | Проблема | Проявление | Корневая причина |
| :-- | :--- | :--- | :--- |
| **O-01** | Отсутствие централизованного логирования и трейсинга. | Трудно найти причину потери конкретного заказа среди трех систем (Shop -> CRM -> MES). | Логи хранятся локально на каждом инстансе EC2. Отсутствует сквозной идентификатор запроса (TraceId) для отслеживания пути заказа. |
| **O-02** | Длительный цикл ручного тестирования. | Задержки релизов до месяца из-за ручного регресса. | Зависимость от одного ручного QA. Отсутствие автоматизированных E2E-тестов и тестов производительности. |
| **O-03** | Отсутствие мониторинга очередей RabbitMQ. | Узнаем о проблемах с заказами только от клиентов или при зависании системы. | Нет алертов на рост длины очереди (Queue Depth), нет мониторинга скорости потребления сообщений. |

### 1.4. Безопасность и Данные (потенциальные риски)

| ID | Проблема | Проявление | Корневая причина |
| :-- | :--- | :--- | :--- |
| **S-01** | Прямой доступ MES API к S3-хранилищу `3d files storage`. | На схеме стрелка `uploads files` идет от `Shop API` к хранилищу, но MES API должен читать файлы для расчета. | Непонятен механизм доступа. Если `MES API` ходит в S3 через интернет или с публичными ключами, это создает угрозу утечки данных клиентов (3D-модели — коммерческая тайна). |

## 3. Приоритизация и обоснование

**Ход рассуждений:**
Приоритеты выстроены по методологии **RICE** (Reach, Impact, Confidence, Effort) с учетом текущей бизнес-ситуации: компания теряет контракты и репутацию.

1.  **Сначала Visibility (Наблюдаемость).** Мы не можем чинить то, чего не видим. `INIT-01` (Трейсинг) — фундамент для диагностики потерянных заказов (самая критичная жалоба бизнеса).
2.  **Затем устраняем бутылочное горлышко.** `INIT-02` (Асинхронный расчет) убивает двух зайцев: убирает таймауты API и позволяет утилизировать ресурсы эффективнее. Без этого дальнейшее масштабирование MES API бессмысленно.
3.  **Quick Win для стейкхолдеров.** `INIT-03` (Кеш MES) — небольшая задача, которая быстро снизит градус недовольства внутри компании (операторы производства), чтобы у нас было время на более сложные архитектурные изменения.

### 3.1. Целевая архитектура через полгода

Через полгода система должна выглядеть следующим образом:

*   **Инфраструктура:** Сервисы развернуты в Kubernetes или хотя бы в Auto Scaling Group (минимум 2 инстанса на каждый критичный сервис). Базы данных переведены в режим Master-Replica (чтение с реплик).
*   **Асинхронный процессинг:** `Shop API` не ждет расчета цены. Запрос уходит в очередь. MES API превращается в **MES Worker** (фоновый обработчик), который масштабируется в зависимости от глубины очереди.
*   **Наблюдаемость:** Внедрен стек Grafana Stack (Loki + Tempo + Prometheus + Grafana). Каждый запрос (от фронта до базы) имеет `x-trace-id`.
*   **CI/CD:** Деплой в прод автоматизирован (канареечные релизы или Blue/Green Deployment) с возможностью отката в 1 клик.

### 3.2. Выбор трех ключевых инициатив на полгода

Если у меня есть возможность выполнить только три пункта из-за ограничений команды (8 человек + я), я выберу следующие:

1.  **INIT-01: Внедрение сквозного трейсинга (Tracing).**
    *   **Почему:** Сейчас мы не знаем, где теряются заказы. Мы теряем контракты прямо сейчас. Без этого инструмента мы не докажем бизнесу, что починили проблему и не локализуем баги в цепочке Shop -> CRM -> MES. Внедрение заголовков W3C Trace Context в Spring Boot (Micrometer) и C# (`System.Diagnostics.Activity`) — задача на пару спринтов для бекендеров.

2.  **INIT-02: Переход на асинхронную обработку расчета стоимости (MES Worker Pattern).**
    *   **Почему:** Это единственный способ справиться с нагрузкой API-пользователей и пиковыми нагрузками без переписывания алгоритма расчета 3D (который мы купили и не можем ускорить в коде). Мы меняем **поведение системы**: вместо "Запрос-Ответ 30 минут" делаем "Запрос-Принято-Очередь". Это избавит клиентов API от таймаутов и позволит экономить на железе (Worker'ы включаются по мере надобности).

3.  **INIT-03: Оптимизация дашборда MES (Кеширование).**
    *   **Почему:** Это **социальный капитал**. Пока мы будем переписывать архитектуру расчетов (что может занять 1-2 месяца), бизнес и операторы должны видеть, что ситуация улучшается. Если дашборд продолжит тормозить, стейкхолдеры могут свернуть проект трансформации, решив, что архитектор "ничего не делает". Это дешевая и быстрая победа, которая купит нам время на реализацию INIT-02.

### 3.3. Дополнительный наём

Для реализации этих планов текущей команде будет тяжело, так как у нас всего 3 бекендера и 1 девопс. Я бы обосновал наём:
*   **Senior Backend Engineer (Python/Go)** на 3-6 месяцев (контракт): для написания вспомогательных сервисов (координатор асинхронных задач, скрипты миграции данных) без отвлечения Java и C# команд от поддержки текущего монолита.
*   **DevOps Engineer (+1)**: критично, так как текущий один инженер не справится с переездом на кластерную инфраструктуру (K8s) и настройкой всего стека мониторинга одновременно с поддержкой текущих релизов.
