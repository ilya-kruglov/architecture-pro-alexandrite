# Выбор и настройка мониторинга в системе

## 1. Мотивация

Внедрение централизованного мониторинга необходимо для перехода от реактивного тушения пожаров (жалобы клиентов, звонки операторов) к проактивному управлению стабильностью сервиса.

**Почему Яндекс Метрики уже недостаточно?**
Метрика ориентирована на фронтенд-взаимодействия реальных пользователей (Real User Monitoring, RUM). После открытия публичного API значительная часть трафика и бизнес-критичных операций (расчет стоимости, создание заказа) происходит через машино-читаемые интерфейсы (MES API), которые Метрика не видит. Мы теряем заказы B2B-партнеров "вслепую".

**Что мониторинг даст компании:**
1.  **Снижение времени простоя (MTTR):** Сейчас мы узнаем о проблеме с зависшим заказом от клиента через 3 недели. С мониторингом мы увидим рост очереди в RabbitMQ или увеличение 500-х ошибок **в течение 1 минуты** после начала инцидента.
2.  **Обоснованное масштабирование:** Вместо гадания, хватает ли серверу CPU или памяти, мы будем видеть тренды утилизации ресурсов и сможем планировать бюджет на инфраструктуру (FinOps).
3.  **SLA для B2B-партнеров:** Для возврата крупных контрактов и продажи API как надежного сервиса нам нужны гарантии доступности. Мониторинг — это база для расчета SLA (например, Uptime 99.9%).
4.  **Выявление узких мест:** Мы точно узнаем, что тормозит дашборд MES: долгий SQL-запрос или медленный диск БД.

## 2. Выбор подхода к мониторингу

Для разных слоев системы применим комбинацию подходов.

| Компонент системы | Подход к мониторингу | Обоснование |
| :--- | :--- | :--- |
| **API Gateway / Веб-сервисы** (Shop, CRM, MES) | **RED** (Rate, Errors, Duration) | Эти сервисы управляются запросами (request-driven). Нам важно знать, с какой скоростью они отвечают (Latency), как часто ошибаются (Errors) и сколько запросов принимают (Rate). |
| **Базы данных и очереди** (PostgreSQL, RabbitMQ) | **USE** (Utilization, Saturation, Errors) | Это физические ресурсы с ограниченной емкостью. Важно следить за насыщением очередей (Queue Depth), утилизацией дискового ввода-вывода и ошибками подключения. |
| **Инфраструктура** (EC2 инстансы) | **USE** | Отслеживаем стандартные ресурсы: CPU, Mem, Disk. |
| **Бизнес-метрики** | **Четыре золотых сигнала** | Нас интересует "Трафик" заказов, "Ошибки" в статусах заказов и "Задержка" прохождения заказа по цепочке. |

## 3. План по метрикам

Я отобрал и расширил список метрик, сгруппировав их по системам и методологии RED/USE.

### 3.1. Метрики для Shop API, CRM API, MES API (RED)

| Метрика (Prometheus формат) | Зачем нужна | Ярлыки (Labels) |
| :--- | :--- | :--- |
| `http_requests_total` | **Rate**: Показывает RPS. Базовый показатель нагрузки. Без него не понять, аномалия с ошибками или просто упал трафик. | `service` (shop/crm/mes), `method` (GET/POST), `endpoint`, `status_code` |
| `http_request_duration_seconds` | **Duration**: Время ответа. Критично для B2B API (MES API). Напрямую влияет на User Experience и таймауты. | `service`, `endpoint`, `quantile` (0.5, 0.95, 0.99) |
| `http_errors_total` | **Errors**: Доля 5xx ошибок. Это наш главный индикатор "Пожар". | `service`, `status_code` |
| `jvm_memory_used_bytes` | **Utilization**: Потребление памяти JVM (для Spring Boot). Поможет настроить `-Xmx` и избежать OutOfMemory. | `service`, `area` (heap/non-heap) |
| `process_cpu_seconds_total` | **Utilization**: Загрузка CPU процессом приложения. | `service`, `instance_id` |

### 3.2. Метрики для Баз Данных (USE)

| Метрика | Зачем нужна | Ярлыки |
| :--- | :--- | :--- |
| `pg_stat_database_numbackends` | **Saturation**: Количество активных подключений к БД. Если оно близко к `max_connections` (обычно 100) — сервисы не смогут подключиться. | `database` (shop/mes) |
| `node_memory_MemAvailable_bytes` | **Utilization**: Доступная память ОС. Если БД съедает всю память, ОС начнет убивать процессы (OOM Killer). | `instance` |
| `node_disk_io_time_seconds_total` | **Saturation**: Время ожидания диска. Для БД критично. Высокий IO wait > 10% — причина медленных запросов. | `instance`, `device` |
| `pg_stat_user_tables_seq_scan` | **Saturation (логическое)**: Количество последовательных сканирований таблиц. Рост этого показателя говорит о неоптимальных запросах (проблема дашборда MES). | `table` |

### 3.3. Метрики для RabbitMQ (USE)

| Метрика | Зачем нужна | Ярлыки |
| :--- | :--- | :--- |
| `rabbitmq_queue_messages_ready` | **Saturation**: Глубина очереди. **Критично!** Рост этой метрики означает, что MES не справляется с расчетами или CRM не успевает создавать заказы. Причина всех потерянных заказов. | `queue`, `vhost` |
| `rabbitmq_queue_messages_unacked` | **Saturation**: Сообщения взяты в работу, но не подтверждены. Зависший консьюмер. | `queue` |
| `rabbitmq_queue_messages_published_total` | **Rate**: Входящий поток сообщений. | `queue` |
| `rabbitmq_disk_space_available_bytes` | **Utilization**: Свободное место на диске. Если диск забьется, RabbitMQ упадет и интеграция остановится полностью. | `node` |

### 3.4. Бизнес-метрики (Кастомные)

Эти метрики не собираются экспортерами автоматически, их нужно внедрить в код приложений (Micrometer / Application Insights).

| Метрика | Зачем нужна | Комментарий |
| :--- | :--- | :--- |
| `orders_created_total` | **Бизнес-трафик**: Количество созданных заказов. Позволяет коррелировать технический RPS с реальной выручкой. | Инкремент при переходе статуса `SUBMITTED`. |
| `order_calculation_duration_seconds` | **Бизнес-задержка**: Время от статуса `SUBMITTED` до `PRICE_CALCULATED`. | Позволит доказать бизнесу, что проблема в расчете 3D. |
| `order_status_stuck` | **Бизнес-ошибки**: Количество заказов, зависших в статусе без движения > 30 мин. | Алерт на потерю заказа в цепочке. |

## 4. План действий (Драфт ТЗ)

Для реализации системы мониторинга предлагается следующий план работ (2-3 спринта).

**Этап 1: Инфраструктура мониторинга (DevOps + Сеньор Бэкенд)**
1.  **Сбор метрик:** Развернуть **Prometheus** в инфраструктуре Yandex Cloud.
2.  **Экспортеры:** Установить агенты на сервера приложений:
    *   `Node Exporter` (CPU, Mem, Disk для Linux).
    *   `PostgreSQL Exporter` (метрики БД).
    *   `RabbitMQ Exporter` (очереди).
3.  **Визуализация:** Развернуть **Grafana**. Создать первый дашборд "Александрит Обзор" с основными RED-метриками всех трех API.

**Этап 2: Инструментирование кода (Java / C# разработчики)**
1.  Подключить **Micrometer** (для Spring Boot: Shop, CRM) и **AppMetrics** (для C# MES API) для отдачи метрик в формате Prometheus по эндпоинту `/metrics` или `/actuator/prometheus`.
2.  Добавить кастомные бизнес-метрики (`orders_created_total`).

**Этап 3: Настройка алертов (Архитектор + Тимлид)**
1.  Настроить **Alertmanager** (часть стека Prometheus).
2.  Создать правила алертов (см. Доп. задание ниже).

## 5. Дополнительное задание: Показатели насыщенности и действия при превышении

В рамках методологии USE я определяю следующие пороговые значения насыщенности и регламент реагирования.

| Система | Метрика насыщенности | Порог | Действие при превышении |
| :--- | :--- | :--- | :--- |
| **MES API** | `rabbitmq_queue_messages_ready` для очереди `price_calculation` | > 100 сообщений более 5 минут | **Уровень 1 (Warning):** Отправить сообщение в Slack/ТГ/MAX канал `#alerts-nonprod`.<br>**Уровень 2 (Critical, > 500):** Автоматически увеличить количество воркеров MES API (через API Yandex Cloud scale set) или отправить сигнал "On-Call" инженеру C#. |
| **Shop DB** | `node_disk_io_time_seconds_total` | > 0.1 (10% времени ожидания) в течение 15 минут | **Действие:** Создать тикет в Jira с приоритетом **High** на команду разработки Shop API. Цель: анализ тяжелых запросов (скорее всего, отчеты или дашборд MES) и добавление индексов / кеширования. |
| **Все API** | `http_request_duration_seconds` (95-й перцентиль) | > 2 секунды для MES API / > 0.5 сек для CRM/Shop | **Действие:** Если алерт сработал одновременно с CPU > 80%, скрипт автоматического масштабирования (Autoscaling) должен добавить +1 инстанс EC2 в балансировщик. |
| **Любой сервис** | Количество свободного места на диске | < 10% | **Автоматическое действие:** Запуск скрипта очистки старых логов или файловых архивов (logrotate). Отправка уведомления DevOps-инженеру с требованием расширить диск. |

**Почему выбраны эти показатели?**
*   **Очередь RabbitMQ:** Это прямое отражение отставания производителя от потребителя. Рост очереди = заказы не обрабатываются вовремя = потеря денег.
*   **IO Wait БД:** Это часто "тихий убийца" производительности. CPU может быть низким, но если диск не справляется с записью логов или чтением данных, сервис тормозит. В облаках (Yandex Cloud) это часто связано с исчерпанием IOPS лимитов диска.
